# Authorization Requirements

## Purpose

Control what authenticated users can do through role-based access control (RBAC): manage
users, roles, and the permissions that gate each capability.

## Actors

- **Administrator** — manages users and roles (requires the relevant write permissions).
- **Any authenticated user** — subject to permission checks on every protected action.

## Functional requirements

### Users
- Create, read (single + paginated list), update, and delete users.
- A user has first/last name, an email-based identity, assigned roles, and direct permissions.
- A user's effective permissions are the union of their direct permissions and their roles' permissions.

### Roles
- Create, read (single + paginated list), update, and delete roles.
- A role has a name, description, and a set of permissions. Roles may be global or scoped to a tenant.

### Permissions
- Permissions are named capabilities (e.g. `Users_Read`, `Users_Write`, `Roles_Write`, `Tenancy_Write`).
- The UI presents permissions as a hierarchical tree (parent/child) for assignment to users and roles.
- Endpoints enforce the required permission via `[AppAuthorize]`.

## Acceptance criteria

- **Given** a caller with the write permission, **When** they create a user/role, **Then** it is persisted with audit fields.
- **Given** a caller without the required permission, **When** they call a protected action, **Then** it is rejected (403).
- **Given** a user assigned a role, **When** their session is resolved, **Then** the role's permissions are included in their effective set.
- **Given** a paginated list request, **When** offset/limit are provided, **Then** a bounded page with a total count is returned.

## Constraints & NFRs

- All create/update/delete operations record audit information (who/when).
- Validation (e.g. required fields, name length) is enforced before persistence.

## Out of scope (today)

- Permission inheritance beyond the role/direct model, dynamic/custom permission definitions, delegated administration.
