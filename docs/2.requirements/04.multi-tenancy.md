# Multi-Tenancy Requirements

## Purpose

Represent customer organizations as tenants and associate users with the tenants they belong
to, enabling tenant-scoped data and roles.

## Actors

- **Administrator** — manages tenants (requires tenancy write permission).
- **User** — belongs to one or more tenants.

## Functional requirements

- **Tenant management** — create, read (single + paginated list), update, and delete tenants.
- A tenant has a name (unique) and an organization.
- **User association** — a user can be linked to one or more tenants.
- **Tenant-scoped roles** — a role may be global or bound to a specific tenant.

## Acceptance criteria

- **Given** a unique tenant name, **When** a tenant is created, **Then** it is persisted with audit fields.
- **Given** a duplicate tenant name, **When** creation is attempted, **Then** it is rejected.
- **Given** a paginated list request, **When** offset/limit are provided, **Then** a bounded page with a total count is returned.
- **Given** a user linked to a tenant, **When** their tenants are queried, **Then** the association is returned.

## Constraints & NFRs

- Tenant data lives in the Admin service (document storage).
- Tenant scoping is applied in application/query logic; there is no automatic row-level filtering or tenant-context middleware.

## Out of scope (today)

- Tenant isolation middleware, per-tenant data partitioning, tenant onboarding workflows,
  edition plans, and subscriptions (these appear in the UI menu but are not implemented).
